## 二、架构取舍与验证结论

### A. 知识服务（本仓库）
- 覆盖一线 SOP 查询、新品知识同步、竞品情报检索、加盟政策问答四类场景；
  采用 RAG 架构（FastAPI + 向量余弦召回 + LLM 生成 + 原文引用），回答可溯源。
- 评测闭环：基于 golden-set 度量召回命中率与忠实度，从机制上抑制幻觉
  （验证案例中把模型对品牌归属的幻觉「上海」纠正为语料口径「A 市」）。
- 方案目标：标准查询从分钟级降至秒级、人工承接量目标下降 30%+；
  当前为架构实现阶段，生产接入规划中。

### B. 后端服务底座（store_tool）
- FastAPI + SQLModel + 路由级 API Key 鉴权 + Alembic 版本化迁移 + Docker；
  含统一错误信封、pytest 单测、配置分离。

### C. 数据可靠性
- 真相源唯一化 + 自愈索引 + 接地测试，避免聚合页空输入覆盖完整旧版。

## 三、「业务 → 架构 → 指标」说明模板

```
1. 业务（Why）：谁、在什么场景、痛什么、规模多大
   → "12 家门店的一线员工，查标准 SOP 靠口口相传，分钟级且易走样。"
2. 架构（How）：关键设计决策与理由
   → "用 RAG 而非直接问 LLM：向量召回锁定资料范围 + 生成带原文引用，
      并用供应商解耦抽象隔离 LLM，避免厂商锁定。"
3. 指标（What）：可量化结果或目标
   → "查询秒级、人工量降 30%+ 为方案目标；架构可行性已用真实 LLM 验证，
      评测闭环中验证了幻觉抑制。"
```

## 五、门店智能体 POC 指标体系（方案）

### 5.1 能力模块与状态

| 能力模块 | 实现方式 | 状态 |
|---|---|---|
| 门店知识问答 | RAG（向量召回 + LLM 生成 + 原文引用） | ✅ 已实现 + 真实 LLM 验证 |
| 一线 SOP / 新品 / 政策检索 | 知识库分层（门店网络/新品/加盟/运营FAQ） | ✅ 已实现 |
| 评测闭环 | golden-set 回归 + 检索命中率阈值 | ✅ 已实现 |
| 数据可靠性 | 真相源 + 自愈索引 + 接地测试 | ✅ 已实现 |
| 门店巡检 / 补货预测 / 智能体编排 | 需接入门店 IoT/POS/库存数据 | 🟡 规划中 |

### 5.2 试点指标（方案目标值，非已验证）

| 指标 | 定义 | 方案目标值 | 状态 |
|---|---|---|---|
| 巡检准确率 | 对巡检问题（SOP 合规/陈列规范）回答与人工复核一致的比例 | ≥ 90% | 🟡 目标 |
| 店长减负率 | 一线重复咨询由智能体承接的比例 | ≥ 60% | 🟡 目标 |
| 补货预测准确率 | 接入库存数据后补货建议与实际上架需求匹配度 | ≥ 85% | 🟡 规划 |
| 单店 ROI | （节省工时成本 - 智能体运行成本）/ 单店年成本 | ≥ 5× | 🟡 规划 |
| 检索命中率 | golden-set 上检索召回命中比例（离线已验证） | ≥ 75% 阈值 | ✅ 已验证 |

### 5.3 落地路径

```
第 0 步（已完成）：知识中台架构 + 真实 LLM 验证 + 评测闭环 + 数据护栏
第 1 步（规划）：接入内部 SOP/新品/竞品文档（数据合规评审）
第 2 步（规划）：接入门店 POS/库存/会员数据，扩展检索范围
第 3 步（规划）：定义试点门店与基线（人工承接量/查询耗时/错误率）
第 4 步（规划）：上线试点，按 5.2 指标体系采集数据，输出 POC 报告
```
